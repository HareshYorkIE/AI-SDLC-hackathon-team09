# vague2tickets — agent rules

This project turns a client call, a Slack thread, a client email, or any messy requirement into a verified PRD and tracker work items. The end-to-end flow is the `vague2tickets` skill (`.claude/skills/vague2tickets/SKILL.md`); the subagents it dispatches live in `.claude/agents/`.

Source search covers every connected resource for that feature: meeting transcripts, Slack, Gmail, Confluence, and existing Jira. A disconnected source is skipped and named. Confirmed conversations and pages are saved verbatim. Existing Jira issues are context, not a new requirement.

## Core guarantees

These hold for every agent, every run.

1. **Trace.** Every requirement, ticket, story, and task cites a source: an exact quote from the transcript, or a decision ID (`D1`, `D2`…) from `decisions.json`. Suggestions, competitor ideas, and code findings inform questions; they are never sources. Every ticket, epic, story, and task also carries `provenance` (`generated_by: vague2tickets`, `run_id`, `local_id`) so a reader can see it was generated by this pipeline. `references` lists a prior Jira issue or code path only when this work changes or recreates something that already exists. An empty list means none was found. Never invent a key or a path.
2. **Ask.** Missing or vague information becomes a question with a suggested answer. Grill it (`.claude/skills/grilling/SKILL.md`): one frontier of the design tree per round, then wait. It stays open until the user answers it. Fill gaps with questions, never with assumptions.
3. **Approve.** Jira writes (creating or editing issues, epics, comments) happen only in the skill's publish step, after the PM replies `APPROVE <run-id>`. The Confluence progress page is the exception: it is created at the start of the run and updated after every step, so a closed chat still shows the requirement and how far it got. That page is not approval to create tickets.
4. **Log.** Every step appends one line to `audit.log` in the run folder and updates the Confluence progress page. The run folder is the checkpoint. A closed chat resumes from the first unfinished step. It does not start the run over, re-ask an answered question, or create a Jira issue that already has the `v2t:<run-id>` label.

## Run folder

Each run writes to `output/<run-id>/`, where `<run-id>` is `YYYY-MM-DD-<feature-slug>`. Each agent writes only its own artifact.

| File                | Written by     | Contents                                               |
| ------------------- | -------------- | ------------------------------------------------------ |
| `transcript.md`     | skill          | Verbatim call transcript + call metadata               |
| `requirements.json` | extractor      | Stated requirements, rejected ideas, contradictions    |
| `questions.json`    | clarifier      | Questions, each with a suggested answer                |
| `decisions.json`    | skill          | The user's answers (`D#`), who answered, when          |
| `prd.md`            | drafter        | PRD, every line cited                                  |
| `tickets.json`      | drafter        | Tickets                                                |
| `gate_report.json`  | gatekeeper     | Per-ticket gate results and status                     |
| `impact.json`       | impact-analyst | Affected repos, paths, owners, risks                   |
| `plan.json`         | planner        | Epics → stories → tasks with timeline                  |
| `scorecard.md`      | evaluator      | Run quality checks, PASS / FAIL verdict                |
| `published.json`    | skill          | Confluence page URL and Jira issue keys/URLs of created items |
| `audit.log`         | all            | `<ISO time> \| <agent> \| <step> \| <result>`          |

JSON shapes for every artifact: `docs/schemas.md`. Read it before writing or validating any JSON artifact.

## Ticket statuses

| Status                | Meaning                                                           |
| --------------------- | ----------------------------------------------------------------- |
| `ready`               | Traces to a source and passes every gate                          |
| `needs_clarification` | Traces to a source, but is vague, incomplete, or not testable     |
| `rejected`            | Cannot be traced to a source: the requirement was invented        |

**Status logic:** traceability fails → `rejected`. Otherwise any other gate fails → `needs_clarification`. Otherwise → `ready`. A `ready` ticket has therefore passed every gate below: nothing vague, nothing missing, nothing still open, and a QA engineer could test it today.

## The five gates

| Gate             | Type        | Passes when                                                                                                     |
| ---------------- | ----------- | --------------------------------------------------------------------------------------------------------------- |
| **Traceability** | Mechanical  | Every quote is an exact substring of `transcript.md` (whitespace-normalized) and every `D#` exists in `decisions.json` |
| **Vagueness**    | Mechanical  | No weasel word in title, user story, or acceptance criteria, unless the same criterion states a measurable threshold |
| **Completeness** | Mechanical  | Actor, capability, and at least one acceptance criterion are present, **and** every number, unit, limit, role, or named value in the ticket's cited quotes also appears in an acceptance criterion — nothing the source specified was dropped while drafting |
| **Resolution**   | Mechanical  | The ticket's `open_questions` is empty — nothing about it is still open or deferred                             |
| **Testability**  | Judgement   | A QA engineer could write a pass/fail test from each acceptance criterion, with no further question, covering every case the source or a `D#` implies (e.g. a named status list gets one criterion per status) |

**Weasel words:** fast, faster, quick, slow, easy, easier, simple, intuitive, user-friendly, better, improved, seamless, robust, scalable, flexible, efficient, modern, clean, nice, ASAP, soon, etc., and/or, some, many, most, various, appropriate, as needed, if possible, optimize.

**Measurable threshold:** a number with a unit or a concrete limit, e.g. "loads in under 2 s at p95", "max 3 clicks", "by 2026-11-15".

Run mechanical gates with code (`grep -F`, a short Python check), not by reading.

## Team directory

The planner assigns tasks from the `hub.york.ie` MCP (internal team directory: discipline, technologies, experience, capacity). Not connected yet — until it is, the planner reads `fixtures/team_directory.json` and says so. Same shape either way (`docs/schemas.md`), so the swap changes nothing downstream.

## Tracker and PRD destination

Tickets go to **Jira**; the PRD goes to **Confluence** in the same publish step, before the issues are created. The page includes the requirements, acceptance criteria, every clarification (question, suggested answer, why, competitor links, and the decision or deferral), the decisions log, and links to the Jira issues. Both need the Atlassian MCP connected and signed into the real site — no separate GitHub/GitLab/Linear path. Non-secret config (site, project key, issue type names, space key) lives in `vague2tickets.config.json` at the repo root; credentials live only in the MCP connection, never in a file.

## Governance

- `output/` holds client data and is git-ignored. Keep tokens, passwords, and API keys out of every artifact.
- Slack and Gmail access is read-only: search and read only. Never send, draft, reply, schedule, react, label, or delete anything in either, during the skill or otherwise.
- Code comparison is read-only and goes through the GitHub MCP: search code, read files, read commits and existing scan alerts. No commits, pushes, branches, PRs, or other writes. A code finding can show that a requirement is already implemented; it is never itself a requirement source.
- Loop limits: at most 3 clarification rounds and 2 draft → gate retries. Past the limit, stop and show the user what is still failing.
- The gatekeeper and evaluator run with fresh context: pass them file paths only, never the drafter's reasoning.
- Plans and timelines are proposals. Label them so in every artifact and message.
